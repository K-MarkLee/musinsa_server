# 한계와 후속 과제

[English](../en/future-work.md) · [README](../../README.ko.md) · [측정 환경](environment.md)

현재까지는 준비된 고정 데이터에서 조회 구조의 전후 비용과 로컬 부하 반응을 확인했다.<br>
후속 과제는 실제 배포 환경, 변경 데이터의 정합성, 옵션 사전 저장 방식, ES 문서 구조로 정리한다.

---

## 실제 배포 환경 검증

로컬에서는 k6·애플리케이션·MySQL·Redis·ES·관측 도구가 한 장비의 CPU·메모리·I/O를 공유했다.<br>
Azure에서는 부하 발생기를 서비스 자원과 분리하고, 실제 배포 구성에서 네트워크와 자원 배치가 지연·처리량에 미치는 영향을 확인한다.

| 확인 항목 | 검증 방법 |
| --- | --- |
| 배포 구성 | 앱·DB·Redis·ES·관측 도구의 실행 위치, CPU·메모리·디스크·주요 버전 기록 |
| 자원과 대기 | JVM·Hikari·Tomcat·ES HTTP 풀과 DB·ES·발생기별 CPU·메모리·I/O 관측 |
| 대표 조회 경로 | 로컬에서 확인한 시나리오를 실행해 목표 RPS·실제 처리량·유지 시간·p95·HTTP 실패·drop 확인 |
| 환경 차이 | 데이터·쿼리·캐시·풀 설정과 네트워크 차이를 함께 기록해 병목 위치 비교 |

로컬과 Azure의 수치를 하나의 전후 개선율로 합치지 않는다.<br>
배포 전에는 계획으로, 실행 후에는 실제 조건·결과·한계로 기록한다.

## 데이터 변경 정합성

대표 가격·썸네일, Redis 사전, ES 검색 문서는 원본과 별도의 저장·갱신 경로를 가진다.<br>
현재 고정 데이터 조회 결과만으로 이 경로들의 변경 전파와 실패 복구가 검증되지는 않는다.

| 대상 | 정합성 과제 |
| --- | --- |
| 목록 대표값 | 옵션 가격·판매 상태·이미지가 변경되거나 삭제될 때 대표 가격·썸네일을 계산하고 갱신하는 정책 |
| Redis 사전 | 원본 사전 변경 시 갱신·무효화 시점, 누락·장애 때의 응답 정책, 여러 인스턴스의 반영 차이 |
| DB→ES 변경 전파 | 상품·옵션·가격·재고 변경의 검색 반영 지연, 전파 실패·중복·순서 변경과 재처리 동작 |
| 전체 재색인 | 변경 중인 데이터로 색인을 재구축할 때 누락·중복을 확인하고 전환·실패 복구 절차 검증 |

먼저 원본 데이터와 변경 후 기대 상태, 허용할 반영 지연을 정한다.<br>
그다음 정상 변경과 전파 실패·재시도에서 목록·상세·검색 결과를 확인한다.<br>
ES refresh 주기를 설정하는 것만으로 DB 변경이 전파되지는 않는다.

데이터 수집·전처리 파이프라인의 완성과 데이터셋 재생성 절차도 남아 있다.<br>
수집·정제·옵션 확장 결과를 재현하고, 원본 변경과 파생 데이터 갱신의 출발점을 명시할 계획이다.

## 옵션 사전: Redis·로컬 메모리·RDB 비교

현재 비교 대상은 색상·사이즈 사전 60개다.<br>
상품 전체 응답이나 가격·재고 캐시가 아니다.<br>
관계 조회 구조와 사전 일괄 조회를 함께 바꿨으므로, 상세 개선율 전체를 Redis 선택의 효과로 분리하지 않았다.

| 방식 | 기대하는 이점 | 확인할 비용과 제약 |
| --- | --- | --- |
| Redis 일괄 조회 | 여러 서버가 공유하는 사전과 갱신 지점 | 네트워크 왕복·직렬화, 장애 의존성, 누락 처리 |
| 프로세스 메모리 | 요청별 네트워크 사전 조회 제거 | 서버마다 초기 적재·갱신·무효화, 배포 시점 차이 |
| RDB 조인·일괄 조회 | 원본과 함께 읽고 별도 캐시 의존성 감소 | DB 왕복·조인·문자열 전송·매핑 비용과 DB 부하 |

RDB도 버퍼풀로 메모리에 있는 데이터를 활용하므로 매 요청이 디스크를 읽는다고 가정하지 않는다.<br>
다른 조회 구조와 응답 필드·정렬·데이터를 고정하고 사전 조회 경로만 바꿔 비교한다.

예열 전후 지연·상세 p95·외부 호출 수·메모리와 함께 사전 변경 반영 시간·장애 동작을 확인한다.<br>
현재 Redis 사전에는 TTL·DB fallback이 없으므로 앞의 정합성 과제에서 누락·장애 정책을 정한 뒤 같은 기대 응답을 기준으로 평가한다.<br>
성능 차이가 작으면 구현·운영의 단순성도 선택 기준으로 삼는다.

## ES 옵션 문서와 상품 중심 nested 모델 비교

현재는 옵션 하나가 ES 문서 하나이고, 상품 공통 필드가 반복되며 `productId` collapse로 상품을 묶는다.<br>
상품을 루트 문서로 두고 옵션을 nested로 구성한 모델을 만들어, 같은 검색 요구를 충족하는지 비교할 계획이다.

| 비교 항목 | 확인할 내용 |
| --- | --- |
| 옵션 조합과 응답 | 같은 옵션의 색상·사이즈 조건, 상품 중복 제거, 정렬·페이지 이동과 관련도 |
| 읽기 비용 | 같은 질의·부하의 평균·p95·처리량, ES CPU·검색 큐 |
| 갱신 비용 | 가격·재고·옵션 변경 시 재색인 범위·시간과 검색 반영 지연 |
| 저장·운영 비용 | 색인 크기, 전체 재구축·전환·실패 복구 |

옵션 조합 조건은 같은 nested 쿼리 안에서 유지한다.<br>
검색어·데이터·가중치·부하를 맞춰 문서 구조의 영향을 비교하고, 응답 의미가 바뀐 경우 이를 구분한다.<br>
Nested에서도 내부 옵션 문서와 질의·점수 계산 비용이 남으므로 문서 수나 collapse 제거만으로 성능 우위를 가정하지 않는다.
