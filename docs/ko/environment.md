## k6 시나리오 선정 기준

테스트는 각 API를 단독으로 실행해 입력과 병목을 분리했다.<br>
시나리오는 실제로 사용자의 사용 패턴을 고려하여 빈도가 높을것으로 예상되는 부분을 염두해두고 작성했다.

| 경로 | 고정 입력 | 선정 이유 |
| --- | --- | --- |
| 홈 목록 | 첫 24개 상품 | 홈 진입에서 반복되는 첫 목록 조회 비용 확인 |
| 초기 스크롤 | 응답 cursor를 이어 1~5페이지 조회 | 초기 탐색의 연속 페이지 조회 비용 확인 |
| 필터 | 10개 필터 조건 × 기본·최저가·최고가 정렬, 첫 24개 | 카테고리·브랜드·성별과 복합 조건·정렬의 영향을 확인 |
| 상세 | 고정 상품 5개 반복 | 같은 옵션 관계를 읽고 조립하는 비용 비교 |
| 검색 | 스커트·블랙 스커트·나이키·나이키 후드, 첫 10개 | 단일 종류, 색상+종류, 브랜드, 브랜드+종류의 입력 비교 |

부하에는 `ramping-arrival-rate`를 사용했다.<br>
실제 처리량은 응답 지연과 drop에 따라 달라질 수 있으므로 목표치와 구분한다.

## 목표 부하를 1,000 RPS로 잡은 이유

출발값은 모바일인덱스 수치를 인용한 2024년 7월 보도의 2024년 6월 MAU 약 549만 명이다.<br>
[수치 확인: 패션인사이트, 2024-07-12](https://www.fi.co.kr/main/view.asp?idx=82843)

목표 부하 산정에 참고한 2024년 6월 무신사 MAU 기사 발췌

![목표 부하 산정에 참고한 2024년 6월 무신사 MAU 기사 발췌](../images/evidence/musinsa-mau-2024-06.png)

MAU만으로는 RPS가 나오지 않고, 목표 RPS는 아래 계획 모델로 고정했다.<br>

| 단계 | 계산 | 결과 |
| --- | --- | ---: |
| MAU | 보도값 | 5,490,000 |
| DAU | MAU × 8/30.<br>한 달에 8일 방문한다고 가정 | 1,464,000 |
| 하루 조회 | DAU × 10.<br>방문마다 상품 조회 API 10회라고 가정 | 14,640,000 |
| 평균 RPS | 하루 조회 / 86,400초 | 169 |
| 피크 RPS | 하루 조회의 50%가 2시간에 몰린다고 가정.<br>7,320,000 / 7,200초 | 1,017 |

시나리오의 유지 목표는 이 피크를 반올림한 1,000 RPS 이다.

실제로는 1,000RPS는 목록·스크롤·필터·상세·검색을 합친 조회의 피크다.<br>
하지면 본 측정에서는 그 값을 API마다 단독으로 걸었다.<br>

## 7분 기준 부하


| 단계 | 목표 RPS | 유지 |
| --- | ---: | ---: |
| 워밍업 | 10 | 30초 |
| 1~4 | 50 / 100 / 250 / 500 | 각 30초 |
| 5 | 750 | 60초 |
| 6 | 1,000 | 120초 |

워밍업 이후 각 단계 진입에 15초 ramp를 두어 총 420초다.<br>
통과 기준은 목표 부하 120초 유지, 유지 구간 p95 1초 미만, HTTP 실패 0·drop 0이다.<br>
시작 30초 뒤 HTTP 실패율 5% 이상 또는 drop 발생 시 중단하도록 했고, 유지 구간 p95도 단계별 지연 평가 후 기준 위반 시 중단하도록 했다.<br>
따라서 HTTP 실패가 5% 미만이어도 0이 아니면 통과는 아니다.<br>
`dropped_iterations`는 사용 가능한 VU가 없어 예정한 iteration을 시작하지 못한 횟수다.<br>
이미 전송한 HTTP 요청의 실패나 ES rejected와 다르다.

## 해석

고정 조건을 반복한 결과에는 캐시·JIT 워밍업 효과가 포함된다.<br>
부하가 높아질수록 시간이 줄었다고 해서 동시성 자체가 성능을 개선했다고 판단하지 않는다.<br>
부하 스크립트의 HTTP 성공 확인은 모든 응답 내용의 정확성 검증을 대신하지 않는다.<br>
입력·설정·워밍업 중 고정한 조건과, 한 장비의 CPU·메모리·I/O 공유로 남은 영향을 구분한다.<br>
같은 장비에서 실행했다는 사실이 자원 경합을 분리 통제했다는 뜻은 아니다.

## 집계 범위와 관측값 읽기

전체 응답 통계는 워밍업·증가·유지를 포함하고, 단계별 통계는 유지 구간만 집계했다.<br>
검색의 중단 행은 증가 구간이다.<br>
단계 경계와 기록 시점 때문에 응답 표본 수가 목표 RPS×시간과 조금 다를 수 있다.

연결·CPU 최대치는 각 실행과 종료 직후 정리 구간을 1초 간격으로 조회한 값이다.<br>
각 최대값은 같은 시각에 발생한 값이 아니며, 성긴 그래프는 짧은 피크를 놓칠 수 있다.<br>
시스템 CPU는 DB 단독 사용률이 아니다.<br>
Jaeger 표본은 한 요청의 구성을 설명하고 전체 평균·p95를 대신하지 않는다.

## 고부하 후속 실험

상세의 Hikari·Tomcat 비교는 기준 부하와 별도다.<br>
VU 사전 할당·상한 1,000, 요청 timeout 5초로 설정하고 성능 기준에 따른 조기 중단을 해제했다.<br>
초기 5분은 50 RPS 30초 → 1,000 RPS 45초 → 1,500 RPS 60초 → 2,000 RPS 75초 → 50 RPS 30초, 각 단계 사이 15초 전환이다.<br>
확장 6분 15초에는 2,000 RPS 이후 15초 전환·3,000 RPS 60초가 추가된다.<br>
설정별 1회다.

최대 지점을 검증할 때는 목표 RPS와 실제 처리량을 구분하고, 지연·오류·drop 기준을 만족한 마지막 유지 구간과 처음 실패한 구간을 함께 기록한다.<br>
경계 부근의 반복 확인 없이 한 번의 최고 처리량을 운영 용량으로 확정하지 않는다.<br>
아직 모든 API의 최대 처리량을 측정한 것은 아니다.

## 단일 요청 비교의 반복 단위

각 실험은 첫 호출과 워밍업을 본 측정에서 제외했다.<br>
아래 표의 추가 실행과 최초 캡처는 같은 집계가 아니다.<br>
실행별 값과 실제 조건은 연결된 문서에 있다.

| 비교 | 입력 | 실행당 본 측정 | 추가 실행 집계 |
| --- | --- | --- | --- |
| 대표 가격 | 일반 첫 페이지 24개 | 30건 | 3회·90건/버전 |
| Keyset | 깊이 0·100·1,000·5,000 | 360건 | 3회·1,080건/버전 |
| 썸네일·DTO | Keyset과 같은 위치 | 360건 | 3회·1,080건/버전; 변경 전 재사용 |
| 상세 | 고정 상품 5개 | 450건 | 3회·1,350건/버전 |
| 필터 인덱스 | 필터 10종 × 정렬 3종 | 2,700건 | 3회·8,100건/상태 |
| 검색 | 고정 검색어 4개 | 360건 | 추가 3회·1,080건/방식; 요약은 초기 화면 포함 4회 평균 |

Keyset·DTO·상세·필터·검색은 각 입력에서 첫 호출 1회·워밍업 4회·본 측정 30건을 한 묶음으로 3번 반복한 것이 실행당 표본이다.<br>
대표 가격은 본 측정 30건짜리 실행을 3회 합쳤다.<br>
준비 요청 수와 정확한 서버·캐시 조건은 각 문서에서 구분한다.

p95는 집계 방식도 확인해야 한다.<br>
필터의 통합 p95는 요청 원본을 합쳐 재계산했지만, 검색 표의 마지막 p95 행은 회차별 p95의 산술평균이다.<br>
최초 화면과 추가 실행의 수치 차이, 코드 시점 차이, 캐시를 비우지 않은 조건을 숨기지 않는다.<br>
전체 개선율을 SQL·캐시·객체 생성 하나의 효과로 분리하지 않는다.
