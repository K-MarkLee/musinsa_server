# 관측 비용의 역습: 부하에 맞춘 로그와 추적 범위

[English](../../en/troubleshooting/observability-overhead.md) · [README](../../../README.ko.md)

---

## 문제

개발할 때 쓰던 DEBUG 로그와 넓은 추적 범위를 그대로 둔 채 부하 테스트를 진행했습니다.<br>
요청이 늘면서 SQL과 바인딩 로그 출력, 스팬 생성과 전송도 함께 늘었고, 애플리케이션과 Jaeger, Grafana 같은 관측 도구가 같은 장비의 CPU, 메모리, 디스크를 나눠 썼습니다.

---

## 조치

| 대상 | 변경 | 효과 |
| --- | --- | --- |
| SQL, 바인딩 로그 | DEBUG, TRACE → INFO | 요청마다 나가던 상세 로그 감소 |
| 추적 범위 | 원인 분석에 쓰지 않는 관측 지점 제거 | 불필요한 스팬 생성과 전송 감소 |
| 트레이스 수집 | 샘플링 1% | 모든 요청을 추적하는 비용 감소 |
| 진단 지표 | 조회, ES 호출 스팬과 연결 풀 메트릭은 유지 | 처리 시간과 대기 위치는 계속 확인 |

관측 범위를 줄인 뒤 응답이 개선됐고, 이후 부하 측정에는 모두 이 설정을 적용했습니다. → [적용 설정](../../../src/main/resources/application-dev.yml)

---

## 선택과 트레이드오프

- **추적 기회**: 샘플링을 낮추면 개별 요청을 추적할 기회가 줄어듭니다.
  그래서 처리량, p95, 오류, 연결 대기는 메트릭으로 보고, Jaeger는 요청 안에서 어디가 느린지 볼 때만 썼습니다.<br>
