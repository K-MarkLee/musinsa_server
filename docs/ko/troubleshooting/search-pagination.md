# 옵션 문서의 중복 제거와 검색 페이지네이션

[English](../../en/troubleshooting/search-pagination.md) · [README](../../../README.ko.md)

---

## 문제

검색 문서를 옵션 단위로 만들었기 때문에, 검색 결과를 그대로 보여주면 같은 상품의 여러 옵션이 목록을 여러 칸 차지했습니다.<br>
검색은 옵션 단위로 하고 화면에는 상품 단위로 보여줘야 하는 차이를 해결해야 했습니다.

---

## 조치: productId로 묶기(collapse)

`productId`가 같은 옵션 문서를 하나로 묶고, 정렬 기준에 맞는 대표 옵션 하나만 상품 목록에 반환했습니다.<br>
관련도순이면 점수가 가장 높은 옵션, 최저가순이면 조건에 맞는 옵션 중 가장 싼 옵션이 대표가 됩니다.<br>
[Collapse 공식 문서](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/collapse-search-results)

```mermaid
flowchart LR
    A[검색 조건] --> B[조건을 만족하는 옵션 문서]
    B --> C[productId별 collapse]
    C --> D[상품별 대표 옵션]
    D --> E[중복 없는 상품 목록]
```

---

## search_after를 쓰지 못한 이유

무한 스크롤에 `search_after`를 쓰려 했지만, collapse와 함께 쓰려면 묶는 필드와 정렬 필드가 같아야 합니다.<br>
상품 ID로 묶으면서 관련도나 가격으로 정렬해야 해서 이 조건에 맞지 않았습니다.

| 대안 | 판단 |
| --- | --- |
| 옵션을 넉넉히 가져와 애플리케이션에서 합치기 | 상품마다 맞는 옵션 수가 달라, 옵션 2,160개(평균 72개 × 상품 30개)를 가져와도 서로 다른 상품 30개를 보장할 수 없습니다. |
| 여러 번 나눠 가져와 합치기 | 중복 제거와 전체 정렬, 페이지 경계 처리를 애플리케이션이 맡아야 합니다. |
| collapse + from/size | ES가 중복 제거와 정렬을 처리하고 상품 단위로 페이지를 나눠 줘서 선택했습니다. |

그래서 커서에 페이지 번호를 담고, `from/size`로 다음 상품 묶음을 조회하도록 했습니다.

---

## 선택과 트레이드오프

- **깊은 페이지**: `from`이 커질수록 앞의 결과까지 모두 모아야 해서 비용이 커집니다.
  다만 검색 결과는 목록처럼 깊게 넘겨 보는 경우가 드물어, 앞쪽 몇 페이지에서는 크게 문제 되지 않습니다.<br>


- **전체 상품 수**: 검색 결과의 전체 건수는 묶기 전의 옵션 문서 수라, 화면에 상품 수를 보여주려면 따로 집계해야 합니다.<br>


- **검색 비용**: 옵션 문서를 매칭하고 점수를 매기는 작업에 상품별 대표를 고르는 처리가 더해집니다. 이 비용은 [검색 병목 조사](search-capacity.md)에서도 확인했습니다.<br>
