# 옵션 문서의 중복 제거와 검색 페이지네이션

[English](../../en/troubleshooting/search-pagination.md) · [README](../../../README.ko.md) · [공통 측정 환경](../environment.md)

## 왜 옵션 단위로 검색했는가

색상·사이즈·가격·재고는 같은 상품 안에서도 옵션마다 다르다.<br>
상품에 색상과 사이즈 배열만 각각 저장하면 실제로 함께 판매하지 않는 조합도 검색될 수 있다.<br>
예를 들어 검정/S와 빨강/M만 판매하는 상품에서 검정/M을 찾는 상황이다.

옵션을 독립 문서로 저장해 같은 옵션의 조건을 함께 평가하도록 했다.<br>
대신 한 상품의 여러 옵션이 검색되므로, 검색 결과를 그대로 반환하면 같은 상품이 목록을 여러 칸 차지한다.<br>
검색 단위는 옵션, 화면의 반환 단위는 상품이라는 차이를 해결해야 했다.

---

## 선택: productId로 collapse

`productId`가 같은 옵션 문서를 하나의 그룹으로 묶고, 정렬 기준에 맞는 대표 옵션을 상품 목록에 반환했다.<br>
관련도순이면 점수가 높은 옵션, 최저가순이면 검색 조건을 만족하는 옵션 중 가격이 낮은 옵션이 대표가 된다.<br>
[Collapse 동작](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/collapse-search-results)

```mermaid
flowchart LR
    A[검색 조건] --> B[조건을 만족하는 옵션 문서]
    B --> C[productId별 collapse]
    C --> D[상품별 대표 옵션]
    D --> E[중복 없는 상품 목록]
```

## 부딪힌 문제: search_after와 정렬 조건

무한 스크롤에 `search_after`를 적용하려 했지만, collapse와 함께 쓰려면 collapse 필드와 정렬 필드가 같고 보조 정렬이 없어야 한다.<br>
상품 ID로 묶으면서 관련도·가격으로 정렬하는 요구와 맞지 않았다.

| 대안 | 판단 |
| --- | --- |
| 옵션을 많이 가져와 애플리케이션에서 병합 | 평균 옵션 72개 × 상품 30개 = 2,160개를 가져와도 상품별 매칭 옵션 수가 달라 고유 상품 30개를 보장하기 어렵다.<br>전송량과 병합 작업도 커진다. |
| 여러 요청으로 나눠 가져와 병합 | 병렬 요청을 하더라도 상품 중복 제거와 전역 정렬·페이지 경계 처리는 애플리케이션에 남는다. |
| collapse + from/size | ES에서 중복 제거와 정렬을 처리하며 상품 단위 페이지를 반환할 수 있어 선택했다. |

현재 커서에는 페이지 번호를 담고 `from/size`로 다음 상품 묶음을 조회한다.<br>
API의 커서 형태를 유지하면서 내부 페이지 이동 방식을 변경했다.

## 선택의 비용

- 깊은 페이지: `from`이 커질수록 앞선 결과까지 수집하는 비용이 늘고 result window 제한을 받는다.<br>
  관련도 정렬도 이 비용을 없애지는 않는다.
- 전체 상품 수: 검색의 total hits는 collapse 전 옵션 문서 수다.<br>
  화면에 고유 상품 수가 필요하면 별도 집계가 필요하다.
- 검색 작업: 옵션 문서의 매칭·점수 계산에 상품별 대표를 고르는 그룹 처리가 더해진다.<br>
  [고부하 조사](search-capacity.md)에서도 검색·점수·그룹 처리 경로를 확인했다.

## 다음 선택지: 상품 문서 + nested 옵션

상품을 최상위 문서로 두고 옵션을 `nested`로 저장하면 같은 옵션 안의 색상·사이즈 조합을 유지하면서 상품 단위로 검색 결과를 받을 수 있다.<br>
상품 중복 제거용 collapse를 없애고 상품 정렬값을 기준으로 `search_after`를 구성하는 대안이다.<br>
[Nested 문서 모델](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/nested)

다만 nested는 내부적으로 옵션을 별도 Lucene 문서로 저장하고 부모 상품과 연결해 검색한다.<br>
옵션 변경 시 상품과 nested 문서 묶음의 재색인 비용도 고려해야 한다.<br>
따라서 전환 기준은 collapse 제거 자체보다 검색 지연·검색 품질·옵션 갱신 비용의 균형이다.
