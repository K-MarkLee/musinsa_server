# 상세 조회: Mock으로 대기와 DTO 조립 병목 좁히기

[English](../../en/troubleshooting/detail-isolation.md) · [README](../../../README.ko.md) · [공통 측정 환경](../environment.md)

---

## 시작점: 길게 보이는 Security 스팬

상세 조회의 처리량이 약 2,000 RPS에서 정체됐고 Jaeger에서는 Security 구간이 길게 보였다.<br>
인증 처리 자체가 느린 것인지, 그 안에 포함된 하위 처리와 대기가 긴 것인지 확인하기 위해 실제 요청 경로를 단계별로 Mock으로 대체했다.

---

## 계층을 바꿔가며 측정

| 단계 | 테스트 경로 | 측정 RPS | 확인한 내용 |
| --- | --- | ---: | --- |
| 1 | Mock Controller + Security 제외 | 41,000 | 단순 응답 경로는 상세 API보다 높은 요청량을 처리했다. |
| 2 | Mock Controller + Security 포함 | 42,000 | Security를 포함해도 처리량이 유지돼 인증 로직보다 하위 경로를 조사했다. |
| 3 | Mock Service + Dummy DB | 66,000 | 실제 비즈니스 로직과 DB 경로를 대체하자 처리량이 크게 높아졌다. |
| 4 | 실제 상세 Service | 2,000 | 실제 관계 조회와 응답 조립 경로로 조사 범위를 좁혔다. |

각 행은 단계별로 처리 경로를 교체한 실험이다.<br>
외부 계층부터 확인하면서 Security 자체를 수정하는 대신 서비스 진입 대기와 실제 상세 처리 내부를 추적했다.

---

## Jaeger와 코드에서 찾은 두 구간

첫째는 서비스 진입 전 대기였다.<br>
바깥 Security 스팬이 길어도 그 시간이 모두 인증 연산은 아니었다.<br>
하위 스팬의 시작 시점과 연결 풀 지표를 함께 확인해, 요청이 실제 서비스 본문을 실행하기 전 기다리는 구간을 찾았다.

둘째는 조회한 데이터를 DTO로 조립하는 구간이었다.<br>
상품·옵션·이미지·옵션값 관계를 탐색하며 응답을 만들 때 지연 로딩과 반복 변환이 함께 발생했다.<br>
여러 일대다 관계를 한 번에 fetch join하면 행이 곱으로 늘어나는 문제도 있어, 쿼리 개수만 줄이는 방식으로는 읽기와 조립 비용을 해결하기 어려웠다.

---

## 조치: 읽는 단위와 조립 순서 변경

상품·옵션·재고, 이미지, 옵션값 매핑을 필요한 단위로 나눠 조회하고 결과를 묶어 응답을 조립했다.<br>
반복해서 사용하는 색상·사이즈 사전은 일괄 조회해 활용하고, 가격·재고는 DB에서 읽도록 했다.

[상세 조회 개선](../improvements/product-detail.md)에는 이 구조 변경의 반복 측정과 70.14→8.91ms 결과를 정리했다.<br>
동시 부하에서 발생한 연결 획득 대기는 [Hikari 조정](hikari.md), 요청 스레드 수의 영향은 [Tomcat 비교](tomcat.md)로 이어서 확인했다.

---

## 판단

가장 긴 바깥 스팬의 이름만으로 원인을 정하지 않고, Mock으로 실행 경로를 줄인 뒤 하위 스팬과 코드를 연결해 조사했다.<br>
그 결과 Security 설정 변경보다 연결 대기와 관계 조회·DTO 조립 구조를 개선하는 데 집중할 수 있었다.
