# 상세 조회: Mock으로 대기와 DTO 조립 병목 좁히기

[English](../../en/troubleshooting/detail-isolation.md) · [README](../../../README.ko.md)

---

## 문제

상세 조회의 처리량이 약 2,000 RPS에서 멈췄고, Jaeger에서는 Security 구간이 가장 길게 보였습니다.<br>
인증 처리 자체가 느린지, 그 안에서 실행되는 다른 처리가 느린지 나누기 위해 요청 경로를 바깥부터 하나씩 Mock으로 바꿔 측정했습니다.

---

## 계층별 측정

| 단계 | 테스트 경로 | 측정 RPS |
| --- | --- | ---: |
| 1 | Mock Controller, Security 제외 | 41,000 |
| 2 | Mock Controller, Security 포함 | 42,000 |
| 3 | Mock Service, Dummy DB | 66,000 |
| 4 | 실제 상세 Service | 2,000 |

Security를 포함해도 처리량이 그대로여서 인증 처리는 원인이 아니었습니다.<br>
실제 서비스와 DB 경로로 바꾸는 순간 처리량이 2,000 RPS로 떨어져, 원인을 상세 서비스 내부로 좁혔습니다.

---

## 찾은 원인

첫째는 서비스에 들어가기 전의 대기였습니다.<br>
Security 스팬이 길었지만 그 안의 대부분은 인증 연산이 아니라, 하위 스팬의 시작 시점과 연결 풀 지표로 보면 서비스 본문이 실행되기 전 DB 연결을 기다리는 시간이었습니다.

둘째는 응답을 조립하는 구간이었습니다.<br>
상품, 옵션, 이미지, 옵션값 관계를 지연 로딩으로 하나씩 읽으며 응답을 만들어 SQL과 변환이 반복됐고, 여러 관계를 한 번에 조인하면 행이 곱으로 늘어나는 문제가 있었습니다.

---

## 조치

관계를 필요한 단위로 나눠 조회하고, 색상과 사이즈 사전은 한 번에 읽도록 바꿨습니다.<br>
이 변경으로 상세 조회 평균은 69.47ms에서 9.11ms가 됐습니다. → [상세 조회 개선](../improvements/product-detail.md)<br>
DB 연결 대기는 [Hikari 실험](hikari.md)과 [Tomcat 실험](tomcat.md)에서 이어서 다뤘습니다.

---

## 판단

가장 긴 스팬의 이름만 보고 Security 설정을 고치지 않고, 경로를 하나씩 바꿔 원인을 좁혔습니다.<br>
그 덕분에 실제 원인인 연결 대기와 관계 조회, 응답 조립 구조에 집중할 수 있었습니다.
