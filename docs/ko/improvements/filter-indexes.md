## 문제와 비교 조건

상품 목록에는 카테고리, 브랜드, 성별 필터와 기본순, 최저가순, 최고가순 정렬이 붙습니다.<br>
대표 가격을 저장한 뒤에도 가격순 정렬에 맞는 인덱스가 없어, 필터를 걸고 가격순으로 보면 여전히 느렸습니다.

`GET /api/products?limit=24`의 첫 페이지를 필터 10가지 × 정렬 3가지, 총 30개 조건으로 조회했습니다.<br>
조건별 첫 요청 1회 → 워밍업 4회 → 1 VU 본 측정 30회를 한 묶음으로 4번 실행했습니다.

## 왜 느렸고 무엇을 줄였는가

필터를 건 가격순 목록은 조건에 맞는 상품을 찾은 뒤 가격순으로 정렬해 상위 24개를 골라야 합니다.<br>
가방 카테고리의 최저가순을 예로 들면, 기존에는 가격 정렬에 쓸 인덱스가 없어 상품 테이블 전체(155,036행)를 읽고 조건에 맞는 39,891행을 모두 정렬한 다음 25개만 반환했습니다.

그래서 판매 여부, 가격, 상품 ID 순서로 정렬된 복합 인덱스와, 같은 순서에 브랜드를 앞에 둔 복합 인덱스를 추가했습니다.<br>
인덱스를 가격순으로 읽다가 조건에 맞는 25개를 찾으면 바로 멈추기 때문에, 읽는 행이 155,036개에서 343개로 줄고 별도 정렬이 사라졌습니다.<br>
최고가순은 같은 인덱스를 거꾸로 읽고, 기본 ID순은 원래 기본 키로 빠르게 찾던 조회라 차이가 거의 없었습니다.

```sql
CREATE INDEX idx_product_price
    ON product (is_available, default_price, product_id);
CREATE INDEX idx_product_brand_price
    ON product (brand_id, is_available, default_price, product_id);
```

| 항목 | 인덱스 미사용 | 인덱스 사용 |
| --- | --- | --- |
| 조회 방식 | 상품 테이블 전체 스캔 | 가격 복합 인덱스 범위 탐색 |
| 읽은 행 | 155,036행 | 343행 |
| 조건을 통과한 행 | 39,891행 | 25행 |
| 별도 정렬 | 39,891행 정렬 | 없음 |
| 실행 시간 | 73.9ms | 1.41ms |

## 선택과 트레이드오프

- **쓰기 비용**: 인덱스가 늘면 상품 등록이나 가격 변경 때마다 인덱스도 함께 갱신해야 하고 저장 공간도 늘어납니다.
  그래서 모든 필터 조합이 아니라 효과가 가장 큰 가격 정렬 경로 두 개만 만들었습니다.<br>


- **카테고리 인덱스 제외**: 카테고리까지 넣은 인덱스도 비교했지만, 상위 카테고리로 조회하면 여러 하위 카테고리를 함께 읽어야 해서 전체 가격순을 바로 얻을 수 없었습니다.
  가방 조건에서 가격 인덱스는 343행만 읽었지만 카테고리 인덱스는 39,891행을 정렬해야 했고, 하위 카테고리 하나만 고를 때만 효과가 있어 제외했습니다.<br>


- **엣지 케이스**: 카테고리나 성별처럼 조건에 맞는 상품이 드물면, 25개를 채우기 위해 인덱스를 더 길게 읽어야 합니다.<br>
