## QueryDSL

| 방식 | 잘 맞는 경우 | 이 프로젝트에서는 |
| --- | --- | --- |
| Spring Data JPA 메서드 이름 조회 | 조건이 단순하고 고정된 조회 | 필터 조합이 늘어날수록 메서드도 계속 늘어남 |
| JPQL (`@Query`) | 조인과 조회 구조가 고정된 조회 | 선택 조건, 정렬, 커서를 문자열로 이어 붙여야 함 |
| JDBC, 네이티브 SQL | DB 기능을 그대로 쓰는 복잡한 SQL | 엔티티 매핑과 타입 검사 없이 직접 관리해야 함 |
| **QueryDSL (선택)** | 조건, 정렬, 조회 컬럼을 코드로 조합하는 조회 | 빌드에서 Q타입 생성 설정이 필요함 |

목록 API는 카테고리, 브랜드, 성별 필터와 정렬, 커서 조건이 요청마다 다르게 조합됩니다.<br>
이런 복잡하고 동적인 조회를 문자열이 아닌 Java 코드로 조합하고, 필요한 컬럼만 DTO로 바로 받기 위해 QueryDSL을 사용했습니다.<br>
대신 빌드 과정에서 Q타입을 생성하는 설정이 추가됩니다.

## MySQL

| 비교 | MySQL (선택) | PostgreSQL |
| --- | --- | --- |
| 팀 숙련도 | 팀원 대부분이 사용해 본 DB | 새로 익혀야 하는 부분이 있음 |
| 관계형 조회 | 조인, 정렬, 복합 인덱스로 충분 | 같은 수준으로 가능 |
| DB 안의 전문 검색 | FULLTEXT 수준 | 전문 검색 기능과 확장이 더 다양 |

이 프로젝트에 필요한 건 일반적인 관계형 조회라, 성능이나 기능에서 우위가 있는 DB를 고르기보다 팀원들의 숙련도가 높은 MySQL을 선택했습니다.<br>
검색까지 DB 안에서 해결하려 했다면 전문 검색 기능이 더 다양한 PostgreSQL을 선택했을 것입니다.<br>
검색은 Elasticsearch로 분리했기 때문에 이 차이는 크게 작용하지 않았습니다.

## Redis

| 방식 | 장점 | 단점 |
| --- | --- | --- |
| 로컬 캐시 | 네트워크 왕복이 없음 | 서버마다 따로 적재하고 갱신해야 함 |
| DB 직접 조회 | 별도 저장소가 필요 없음 | 요청마다 DB에 부하가 감 |
| **Redis (선택)** | 서버가 나뉘어도 한곳에서 공유하고, DB 부하가 없음 | 네트워크 왕복이 생기고, 갱신과 장애 대응이 필요함 |

색상, 사이즈 같은 옵션값과 카테고리는 거의 바뀌지 않는 데이터입니다.<br>
서버가 여러 대로 나뉘어도 같은 값을 쓸 수 있게 독립된 저장소에 두고, 이 데이터를 읽기 위한 DB 부하를 아예 없애려고 Redis를 사용했습니다.<br>
다만 Redis 조회에도 네트워크 왕복이 든다는 점은 처음에 충분히 고려하지 못했고, 값이 바뀌거나 Redis가 응답하지 않을 때의 처리도 추가로 필요합니다.

## Elasticsearch

| 방식 | 검색 방식 | 이 프로젝트에서는 |
| --- | --- | --- |
| LIKE | 상품명에서 연속된 문자열 찾기 | "블랙 스커트"처럼 여러 필드에 흩어진 검색어를 찾지 못함 |
| MySQL FULLTEXT | 단어 단위 검색과 관련도 | 한국어 형태소 분석, 동의어, 필드별 가중치를 세밀하게 다루기 어려움 |
| **Elasticsearch (선택)** | 형태소 분석, 동의어, 여러 필드 검색과 가중치 | 별도 서버를 운영하고 DB와 동기화해야 함 |

사용자의 검색어에는 색상, 종류, 브랜드가 섞여 있고, 이 정보는 상품명, 옵션, 카테고리에 흩어져 있습니다.<br>
단어마다 여러 필드 중 하나 이상에 맞아야 하는 조건(`minimum_should_match`)을 세밀하게 다뤄야 했고, 한국어 상품명을 단어로 나누는 Nori 분석기와 색상, 사이즈 동의어가 필요해 FULLTEXT 대신 Elasticsearch를 선택했습니다.<br>
다만 실제로 판매하는 옵션 조합만 찾으려면 옵션 단위로 검색해야 해서, 같은 상품을 묶기 위한 collapse나 nested 같은 추가 설계가 필요했습니다.

## 부하 테스트와 모니터링

| 도구 | 쓴 이유 |
| --- | --- |
| k6 | 초당 요청 수를 정해 부하를 걸고, 시나리오와 통과 기준을 코드로 남기기 위해 |
| Prometheus | Hikari 연결, Tomcat 스레드, ES 연결 풀 같은 지표를 시간에 따라 수집하기 위해 |
| Grafana | 처리량, 지연, 자원 지표를 같은 시간축에 놓고 언제 무엇이 변했는지 보기 위해 |
| Jaeger | 요청 하나 안에서 어느 구간에 시간이 쓰였는지 보기 위해 |
| ES Profile | 검색 쿼리에서 어떤 연산이 비싼지 보기 위해 |
| ES hot threads | 부하 중 ES가 CPU를 어디에 쓰는지 보기 위해 |

부하를 거는 도구와 시간에 따른 지표, 요청 하나의 내부를 함께 봐야 "언제 느려졌고, 그때 무엇이 쌓였고, 요청 안에서 어디서 기다렸는지"를 연결할 수 있었습니다.
